# My Omarchy macOS 管理界面设计文档

## 1. 概述

### 1.1 背景与问题

当前 macOS App 在启动 VM 前展示单页 `StartMenuWindow`。权限、共享目录、端口转发、资源档位、启动模式、存储位置和 Factory Reset 被堆叠在同一个滚动窗口中；VM 启动后该窗口被隐藏并销毁，用户无法通过稳定入口查看运行状态、重新打开设置或执行诊断。

随着原生音频、摄像头、剪贴板、共享目录、端口转发、资源策略、存储安全和恢复能力增加，单页启动菜单已经无法清晰表达各项能力的归属、状态和生效时机。当前界面还存在以下限制：

- 设置项缺少稳定的信息架构，常用操作与危险操作混在同一页面；
- 界面只使用英文硬编码文本，不能跟随 macOS 系统语言；
- VM 生命周期状态主要由控制器内部布尔值和模态提示表达，页面不能持续展示运行过程；
- VM 运行时原生管理入口消失，启动、运行、停止和错误恢复不能形成闭环；
- 诊断与恢复规范中的未来能力容易与当前已实现能力混淆。

### 1.2 目标

1. 用常驻的五页管理窗口完全替代现有启动菜单，形成唯一的 App 管理入口。
2. 保留 AppKit 应用生命周期、命令行辅助模式和现有运行时控制逻辑，使用 SwiftUI 实现管理页面。
3. 以一个统一状态模型驱动首次准备、启动、运行、停止、重启和失败恢复界面。
4. 首发支持跟随系统语言的中文和英文界面。
5. 保持现有权限、存储、共享目录、端口转发、资源档位、启动模式与重置行为的安全语义。
6. 只展示当前真实可用的产品能力，为未来诊断、升级和备份能力保留内部扩展边界，但不显示不可用入口。
7. 满足 macOS 原生交互、键盘操作、VoiceOver、高对比度和 Reduce Motion 要求。

### 1.3 非目标

- 不在本功能中实现诊断包、稳定错误码注册表、无损升级、备份或恢复。
- 不把 SwiftUI `App` 设为应用入口，也不重写 `main.swift` 的多命令分派。
- 不改变 QEMU 参数、guest ABI、存储格式、端口转发协议或各 native bridge 协议。
- 不引入第二套 VM 生命周期、权限、偏好或危险操作执行逻辑。
- 不保留旧启动菜单作为长期备用界面。
- 不在本功能中新增菜单栏常驻项。

## 2. 已确认的产品决策

| 决策 | 结论 |
|------|------|
| 导航结构 | 五页平衡型：概览、虚拟机、集成、权限、诊断 |
| 视觉方向 | 原生混合：原生 macOS 结构和控件，克制使用 My Omarchy 蓝紫色品牌强调 |
| 入口关系 | 新管理窗口完全取代现有启动菜单，概览页是唯一启动入口 |
| VM 运行期间 | 管理窗口继续可用，提供状态、停止、重启和诊断入口 |
| 首次启动 | 仍进入概览页，通过步骤卡完成准备，不增加独立向导 |
| 语言 | 跟随 macOS 系统语言，首发支持中文和英文 |
| UI 技术 | AppKit 管理应用生命周期和窗口，`NSHostingView` 承载 SwiftUI 页面 |
| 生命周期事实源 | `VMApplicationController` 保持唯一执行者和事实源 |

## 3. 用户场景

### 场景 1：首次准备

**Given** 用户第一次启动 My Omarchy，运行时或 VM 尚未准备完成

**When** 管理窗口打开

**Then** 概览页按当前可观测信号展示权限检查、启动前配置和 VM 启动步骤，每一步显示进行中、完成、降级或失败状态，并允许在可重试阶段重试

### 场景 2：启动与运行管理

**Given** VM 已准备完成

**When** 用户从概览页启动 VM

**Then** 概览页展示真实启动阶段，VM 图形窗口出现后管理窗口仍可使用，并提供打开虚拟机、停止、重启和诊断操作

### 场景 3：修改下次启动配置

**Given** VM 正在运行

**When** 用户查看资源档位、启动模式、存储位置或端口转发等冷启动配置

**Then** 当前值保持可见，不能安全热更新的控件禁用并明确标注“下次启动生效”或“停止虚拟机后可修改”

### 场景 4：权限被拒绝

**Given** 用户拒绝麦克风或摄像头权限

**When** 用户启动 VM 或返回权限页

**Then** VM 仍可启动，对应集成显示降级状态，并提供打开正确 macOS 系统设置页面的操作

### 场景 5：启动失败

**Given** 启动在存储准备、QEMU、QMP 或 guest 启动阶段失败

**When** 控制器确认失败

**Then** 概览页保留错误摘要、失败阶段、重试和查看诊断入口；切换页面不会清除错误，界面不会自动执行 Factory Reset

### 场景 6：关闭管理窗口

**Given** VM 正在运行

**When** 用户关闭管理窗口

**Then** 窗口只隐藏，VM 和 App 继续运行；用户可通过 Dock 图标或 App 菜单中的“打开 My Omarchy”恢复窗口

## 4. 方案选择

### 4.1 方案 A：纯 AppKit

继续使用 `NSWindow`、`NSView` 和手写约束构建五页界面。它与现有代码最接近，但复杂表单、状态绑定、本地化、可访问性和后续维护成本最高。

### 4.2 方案 B：AppKit 生命周期 + SwiftUI 页面（采用）

保留现有 `main.swift`、`NSApplication`、`VMApplicationController` 和命令行辅助模式；由 AppKit 创建管理窗口，通过 `NSHostingView` 承载 SwiftUI 根视图。

该方案提供 SwiftUI 在侧边栏、表单、状态卡、本地化和局部刷新的主要收益，同时将高风险的进程生命周期、信号处理、QEMU 窗口协作和辅助进程分派留在已验证的 AppKit 路径。

### 4.3 方案 C：SwiftUI `App` 生命周期 + AppKit 补充

使用 `WindowGroup`、`Commands` 和 SwiftUI scene 管理应用。长期结构统一，但会重构当前同一可执行文件承担的 `--run-qemu`、`--bridge-*` 等入口，重新验证信号退出、激活策略、窗口恢复和 QEMU 协作，超出本次界面改造的必要范围。

## 5. 信息架构

### 5.1 管理窗口

- 窗口标题为“My Omarchy”，默认内容尺寸约 `860 × 620 pt`。
- 左侧固定显示五个一级页面和搜索框，右侧显示当前页面。
- 窗口允许缩放；达到最小尺寸后右侧内容滚动，侧边栏结构保持稳定。
- 搜索仅匹配设置项标题和说明，选择结果后跳转到对应页面并聚焦目标，不搜索日志正文。
- 关闭按钮只隐藏窗口；显式“退出 My Omarchy”才进入现有安全关机与终止流程。
- VM 运行期间 App 保持 `.regular` activation policy 和 Dock 身份，不再切换为当前的 `.accessory` 模式；QEMU 图形窗口不能取代管理窗口在 App 生命周期中的主入口地位。
- App 菜单和 Dock 重新激活都恢复既有管理窗口，不创建第二个窗口。
- 窗口恢复时保持最后访问页面；应用出现关键错误时可以将用户带回概览页，但不能清除其原页面状态。

### 5.2 概览

概览页是唯一的启动与总状态入口。

首次准备状态展示步骤卡：

1. 权限检查；
2. 启动前配置；
3. VM 启动。

步骤只能由当前代码可可靠观测的控制器事件推进，不显示基于计时器伪造的百分比。首版可区分预检、启动器进程运行、QEMU/QMP 已就绪和退出结果；`guest boot`、`graphical ready` 等阶段只有在诊断规范定义的受约束 guest health 协议落地后才能增加。权限中的可选项可以显示“已跳过”或“功能受限”，不能阻塞整个准备流程。

准备完成后展示：

- VM 总状态；
- Apple Silicon、硬件加速和实际资源档位摘要；
- 需要用户处理的最高优先级问题；
- 随状态变化的主操作：启动、打开虚拟机或重试；
- 运行时长和停止、重启入口。

停止和重启必须明确作用于 guest。正常停止优先通过现有安全关闭路径；只有超时后才可展示强制停止，并警告数据风险。

### 5.3 虚拟机

该页承载 VM 本身的配置和数据生命周期入口：

- 启动模式：沉浸式全屏或普通窗口；
- 资源配置：自动或低资源，并展示本机计算出的实际 CPU 和内存；
- 存储位置、卷状态、逻辑容量和宿主实际占用；
- 打开 VM 数据目录；
- 恢复出厂设置。

运行期间不能安全热更新的控件保持可读但禁用，显示“停止虚拟机后可修改”或“下次启动生效”。逻辑容量和实际占用必须分别标注，不能将 sparse disk 的逻辑容量描述为已经使用空间。

Factory Reset 位于页面底部的独立危险区域，继续要求输入 `My Omarchy`，并复用当前的 workspace 身份校验、空间估算和非目标目录保护。

### 5.4 集成

该页承载 Mac 与 guest 的连接能力：

- 共享 Mac 文件夹及启用状态；
- TCP/UDP 端口转发和 SSH 预设；
- 当前有效的音频输入输出路由摘要；
- 双向剪贴板状态；
- 摄像头桥接状态。

每项同时显示配置和运行状态，例如“已配置，下次启动启用”“运行中”“权限缺失”或“桥接已降级”。首版音频项只读展示当前使用系统默认设备或环境配置解析出的有效路由；它不新增当前启动菜单并不具备的音频设备选择 UI。页面只展示当前代码真实支持的操作；未实现的共享类型、网络模式或设备能力不得以禁用占位项出现。

### 5.5 权限

辅助功能、麦克风和摄像头分别显示：

- 已允许；
- 未决定；
- 已拒绝；
- 受限制。

未决定时提供系统授权请求；已拒绝或受限制时提供对应系统设置入口。App 每次重新激活后刷新状态，处理用户从系统设置返回的场景。

文案必须明确辅助功能对原生 Command/Super 体验的影响，以及麦克风、摄像头是可选集成；缺少可选权限不得阻止 VM 启动。

### 5.6 诊断

第一版仅展示已有可靠信号：

- 当前或最近一次启动阶段；
- 最近一次错误摘要；
- 当前已有的启动诊断日志；
- 打开日志目录；
- 复制经过现有脱敏逻辑处理的诊断摘要。

诊断与故障恢复规范中尚未实现的稳定 `MYO-*` 错误码、诊断 zip、完整事件链和高级恢复动作不得在界面中伪装为可用功能。代码边界允许未来以新的状态字段和命令接入，但当前界面不展示占位按钮。

## 6. 技术架构

### 6.1 生命周期与呈现边界

```text
main.swift / NSApplication
          |
          v
VMApplicationController  -- 唯一生命周期与危险操作执行者
          | 发布不可变状态快照 / 接收语义化命令
          v
ManagementViewModel      -- SwiftUI 可观察适配层
          |
          v
ManagementWindow (AppKit NSWindow)
          |
          v
NSHostingView<ManagementRootView>
          |
          +-- OverviewView
          +-- VirtualMachineView
          +-- IntegrationsView
          +-- PermissionsView
          +-- DiagnosticsView
```

AppKit 继续负责：

- 命令行参数和 `--bridge-*` 辅助模式分派；
- `NSApplication` 生命周期、激活策略、菜单和信号；
- 管理窗口创建、显示、隐藏和恢复；
- `NSOpenPanel`、系统权限跳转及需要 AppKit 的 sheet；
- QEMU 图形窗口与应用退出协作。

SwiftUI 负责：

- 五页布局、侧边栏、搜索、表单和状态卡；
- 根据状态快照进行确定性渲染；
- 将用户动作转换为语义化命令；
- 中英文文案、可访问性标签和系统外观适配。

### 6.2 状态模型

`ManagementViewModel` 只保存可渲染状态，不拥有 QEMU `Process`、QMP 连接、存储事务或权限请求。状态快照至少包括：

- `sessionID`：当前运行或启动尝试的唯一标识；它只用于 UI 异步事件隔离，不冒充诊断规范中的持久化 session 协议；
- `readiness`：权限、启动前配置和运行时可用性检查的结果；
- `lifecycleState`：空闲、启动中、运行中、停止中、重启中、错误；
- `startupStage`：首版只包含当前可可靠观测的预检、启动器进程运行、QEMU/QMP 已就绪和退出结果；未来可在受约束 guest health 协议落地后扩展 guest 启动和桌面就绪；
- `configuration`：启动模式、资源偏好、实际资源、存储和集成配置；
- `permissions`：辅助功能、麦克风、摄像头状态；
- `integrationRuntime`：音频、摄像头、剪贴板、共享目录和端口映射的有效状态；
- `lastFailure`：当前可用信号支持的失败摘要、阶段和安全动作；
- `operation`：当前互斥的耗时操作及其是否允许取消。

状态快照由 `VMApplicationController` 在主 actor 上发布。SwiftUI 页面不得通过进程探测或直接读取多个存储对象来推导第二份事实。

### 6.3 命令模型

页面发出的命令使用语义化枚举或明确方法，例如：

- 启动、打开 VM 窗口、安全停止、重启；首次准备由启动命令触发的真实预检和启动器事件表达，不创建独立的伪准备任务；
- 更新启动模式或资源档位；
- 选择、启用或停用共享目录；
- 编辑端口映射；
- 请求权限或打开系统设置；
- 打开 VM 目录、打开日志目录或复制诊断摘要；
- 请求 Factory Reset。

`ManagementViewModel` 将命令转交 `VMApplicationController`。控制器继续调用现有 preference store、QEMU supervisor、QMP、storage controller 和 bridge 能力。页面不得直接执行删除、启动进程或修改磁盘。

### 6.4 AppKit 适配器

以下能力第一阶段通过薄适配器复用，不在 SwiftUI 中重写业务语义：

- 文件夹和存储位置选择；
- 端口转发编辑器及校验模型；
- 权限请求后窗口恢复；
- boot recovery 确认；
- Factory Reset 输入确认；
- 错误细节 sheet。

适配器只负责呈现和回调，不持有独立状态。后续是否迁移为 SwiftUI sheet 由单独任务决定。

## 7. 生命周期与交互规则

### 7.1 状态迁移

```text
空闲 -> 启动中 -> 运行中 -> 停止中 -> 空闲
  |       |          |          |
  +-------+----------+----------+-> 错误

运行中 -> 重启中 -> 启动中
```

首次准备步骤由独立 `readiness` 表达，不伪造成与 QEMU 并列的长生命周期任务；不满足必要预检时，主状态保持空闲并显示对应阻塞项。

- 每次准备或启动创建新的 `sessionID`。
- 异步回调必须携带其所属 session；旧 session 的延迟事件不得覆盖当前状态。
- 同一时间只允许一个会改变 VM 或存储的操作。
- 界面不乐观假设成功；只有控制器确认操作结果后才更新终态。
- VM 图形窗口被遮挡或最小化时，“打开虚拟机”负责通过稳定标识激活并置前，不重复启动。建立可靠的 QEMU Cocoa 窗口定位机制是交付该操作的前置条件；不能用再次启动代替，也不能在验收版本中隐藏该操作。

### 7.2 重启与停止

- 安全停止是默认路径。
- 重启严格执行“安全停止完成，再以新 session 启动”，不能并行启动第二个 QEMU。
- 安全停止超时后才显示强制停止，且必须提示可能导致 guest 数据损坏。
- 用户关闭管理窗口不会触发停止；用户显式退出 App 时继续使用现有终止协调流程。

### 7.3 配置生效时机

设置必须标记为以下三类之一：

1. 立即生效：例如页面导航和可安全即时调整的宿主 UI 偏好；
2. 下次启动生效：例如启动模式、资源档位及需要重建 QEMU 参数的配置；
3. 停止后可修改：例如存储位置和涉及持久 VM 安全边界的操作。

运行中禁止编辑的控件不能悄悄接受值后失败；应直接禁用并显示原因。

## 8. 错误处理与安全边界

- 普通字段错误就地展示，不使用阻断整个窗口的模态对话框。
- 关键启动错误在概览页持续展示，直到新 session 成功或用户明确关闭。
- 同时出现多个信号时，界面展示一个主问题并保留其他影响；在稳定错误分类器实现前不得生成虚假的 `MYO-*` code。
- 外置存储断开、Mac 唤醒恢复失败和 workspace 不兼容等数据风险场景不得自动 Reset。
- boot recovery 继续要求一次性明确同意，且不能被普通“重试”隐式触发。
- Factory Reset 不能成为启动失败页的默认动作，且保持独立输入确认。
- 诊断文案和复制内容复用已验证的脱敏边界，不暴露 API key、环境变量值、用户名、HOME、共享目录内容或用户文件。
- 对尚未实现的诊断能力，界面应缺席而不是显示永远不可用的按钮。

## 9. 本地化、视觉与可访问性

### 9.1 本地化

- 使用 Swift Package 能打包并由 `Bundle.module` 读取的字符串资源统一管理文案；若实施验证证明 String Catalog 在当前命令行构建与 App 打包链路中可稳定产出，则优先使用 String Catalog，否则使用 `.strings` 资源。
- 基础本地化为英文，首发提供简体中文。
- 默认跟随 macOS 针对 App 的语言设置，不增加 App 内语言切换。
- 业务状态和错误保存语义化值；视图层在渲染时本地化，不在控制器中保存最终显示字符串。
- 参数化文案使用本地化插值，避免字符串拼接破坏中英文语序。

### 9.2 视觉系统

- 使用 macOS 原生 sidebar、list、form、toggle、picker、button 和 sheet 语义。
- 品牌色仅用于 App 图标、概览状态卡、选中态和关键状态强调。
- 支持系统浅色、深色和提高对比度模式，不强制 Tokyo Night 深色背景。
- 状态同时使用图标、文字和颜色，不能仅通过红绿表达。
- 动画服从 Reduce Motion；必要状态变化即使关闭动画也必须清晰。

### 9.3 可访问性与键盘

- 所有操作可通过键盘到达，Tab 顺序与视觉阅读顺序一致。
- 侧边栏支持方向键和标准选择行为。
- 图标按钮提供可本地化的 VoiceOver label 和 help。
- 动态状态变化对 VoiceOver 使用适度公告，不重复播报持续更新的数据。
- 中文、英文和较长错误信息允许换行，关键操作标签不得因窗口缩放被截断。

## 10. 迁移方案

1. 为当前控制器行为建立状态快照和命令协议测试，覆盖既有安全语义。
2. 将现有布尔状态收敛为可发布的统一生命周期状态，但不改变 QEMU、存储或 bridge 行为。
3. 创建 AppKit `ManagementWindow` 和 SwiftUI `ManagementRootView`，实现侧边栏、搜索和窗口隐藏/恢复。
4. 将运行期 activation policy 保持为 `.regular`，增加 App 菜单与 Dock 激活时恢复同一管理窗口的路径，并建立既有 QEMU Cocoa 窗口的稳定激活机制。
5. 依次迁移概览、虚拟机、集成、权限和诊断页面。
6. 通过 AppKit 适配器接入现有文件选择、端口编辑、权限、boot recovery 和 reset 确认。
7. 增加英文、简体中文资源及本地化测试。
8. 完成功能等价、自动化测试和 Apple Silicon 真机验证后，删除 `StartMenuWindow`。
9. 更新 README 和 `macos/README.md` 中“启动菜单”“启动后原生窗口让位”等过时说明。

迁移期间允许旧窗口代码存在于分支中用于比对，但同一个构建不得提供两个业务入口或维护两份业务逻辑。

## 11. 边界情况

| 场景 | 处理方式 |
|------|----------|
| 首次准备很慢 | 展示真实阶段和解释，不显示伪百分比；仅在阶段支持时提供重试 |
| 用户连续点击启动 | 命令门控只接受一次，后续点击在当前操作完成前无效 |
| 旧 session 延迟回调 | 通过 `sessionID` 丢弃，不改变当前快照 |
| VM 运行时关闭管理窗口 | 只隐藏窗口，VM 继续运行 |
| VM 窗口已存在时再次点击主按钮 | 激活现有窗口，不创建第二个进程 |
| 运行中修改冷启动配置 | 控件禁用并说明生效条件 |
| 权限请求后返回 App | 在应用激活回调中重新读取权限状态并刷新窗口 |
| 可选权限被拒绝 | 相应集成降级，VM 仍可启动 |
| 外置 VM 卷断开 | 保持安全状态，展示恢复提示，不回退并操作默认目录 |
| Mac 唤醒后 QMP 恢复失败 | 保持 VM 暂停，提供重试或退出，不自动强制恢复 |
| 安全停止超时 | 明示风险后才提供强制停止 |
| 本地化缺少键值 | 测试失败；发布构建不得静默显示内部 key |
| 日志入口不可用 | 展示诊断降级，不阻断停止或退出 |

## 14. 验收标准

1. 打开 App 只出现新的五页管理窗口，不再出现旧启动菜单。
2. 概览页覆盖首次准备、已就绪、启动、运行、停止、重启和失败状态。
3. VM 运行时管理窗口保持可用；关闭窗口不停止 VM，Dock 或 App 菜单可以恢复窗口。
4. 五页覆盖旧启动菜单的全部用户能力，且每项配置的生效时机准确可见。
5. `VMApplicationController` 是 VM 生命周期和危险操作的唯一事实源；SwiftUI 页面不直接执行进程或存储操作。
6. 同一时刻不会启动两个 QEMU，旧 session 事件不能覆盖当前状态。
7. 麦克风和摄像头拒绝只导致对应能力降级，不阻止 VM 启动。
8. Factory Reset 仍要求输入 `My Omarchy`，诊断或重试流程不能绕过确认。
9. 英文和简体中文跟随系统 App 语言正确显示，不暴露内部本地化 key。
10. 浅色、深色、高对比度、Reduce Motion、键盘和 VoiceOver 验证通过。
11. 未实现的诊断、升级、备份和恢复能力不出现在可操作界面中。
12. 现有功能测试、`make full-check` 和 Apple Silicon 真机验收全部通过后，旧 `StartMenuWindow` 才可删除。
